# v0.9.100 IACC MemoryCase and Playbook

## Goal

Close the learning gap in the IACC operational loop by promoting resolved incidents into reusable `MemoryCase` records and deriving `Playbook` candidates for similar future incidents.

## Implemented Capabilities

- Added runtime models:
  - `IaccMemoryCase`
  - `IaccPlaybook`
  - `IaccPlaybookStep`
  - `IaccCasePromotion`
- Added durable SQLite tables:
  - `iacc_memory_case`
  - `iacc_playbook`
- Added IACC store operations:
  - promote incident to memory case
  - get/search memory cases
  - upsert/get playbooks
  - recommend playbooks for an incident
- Added API routes:
  - `POST /api/iacc/incidents/:id/cases/promote`
  - `GET /api/iacc/cases/:id`
  - `GET /api/iacc/cases/search`
  - `POST /api/iacc/playbooks/upsert`
  - `GET /api/iacc/playbooks/:id`
  - `POST /api/iacc/incidents/:id/playbooks/recommend`
- Added health capabilities:
  - `memory_case_promotion`
  - `playbook_recommendation`

## Design Boundary

MemoryCase is not a replacement for the structured fact ledger. It stores the closed-loop summary, root-cause explanation, action record, receipt refs, feedback, and reusable memory summary. Large structured data remains in the IACC store and future production data substrate.

Playbook is a reusable operating procedure candidate. It is generated from a resolved case and can be recommended for a similar incident, but execution still goes through quality gates and cross-plane governance.

## Acceptance

Run:

```bash
scripts/v09100_iacc_memory_case_playbook_scenario.sh
```

Expected result:

- facts ingest
- metrics recompute
- evidence build
- incident create
- analysis
- action execute
- feedback closes incident
- incident promotion creates a memory case and playbook
- case get/search works
- playbook get works
- similar incident receives a playbook recommendation
