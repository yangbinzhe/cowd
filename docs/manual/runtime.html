RUNTIME 与协同执行

从用户输入到可证明结果

Runtime 让模型拥有策略和语义判断空间，同时把身份、权限、依赖、并发、幂等、恢复和终态提交收回确定性内核。团队不是特殊模式，而是 ExecutionGraph 中可被模型提议、由内核约束的一种拓扑。

业务对象与运行对象

对象拥有不拥有
Session交互、Turn、消息顺序、恢复、权限上限Mission 成员、团队编排
Mission长期目标、Root Task 聚合、全局控制聊天记录、Provider 循环
Task目标、验收、状态、Mission 主归属Agent 身份与完整历史
ExecutionGraph依赖、并行、取消、恢复、终态提交长期业务身份

一次 Turn 的完整链路

01
可靠接纳

Gateway 认证入口，Session 保存输入信封和幂等信息；外部消息先进入 Surface inbox。

Gateway / Session
02
Task 路由

显式 focus 优先；无歧义时使用确定性规则，有多个候选或复合目标时允许 Provider 给出受约束提议。

Runtime::Task
03
上下文编译

按模型窗口、输出预留、工具 schema、热历史、记忆与事实证据动态分配预算，必要时建立语义检查点。

Context Runtime
04
策略与协作提议

模型可选择 direct、plan-act、ReWOO、team、review 或 recovery，并声明语义依赖和预期产物。

Model + Runtime
05
权威绑定与图编译

Runtime 解析实际 Agent revision、Team run、Skill/Tool grant、权限、资源租约和物理 ID，再验证 DAG。

Orchestration
06
受控并发执行

无依赖节点并行；Team 展开为 Agent 子图；幂等工具可批量执行；副作用动作经过策略与审批。

Supervisor
07
验证与终态提交

Claim、Evidence、产物和完成条件形成验收账本；失败可重规划、恢复或明确阻塞，不能伪造成功。

Verification
08
投影与回传

canonical activity、关系、证据和 usage 进入持久事件，再由 Gateway 以快照、增量和实时流交给 Surface。

Projection

多 Agent 与团队如何工作

Team Template / model proposal
└── Team Run
    ├── researcher × N        (parallel when independent)
    │   ├── Agent Instance 1
    │   │   └── Tool batch → evidence → artifact
    │   └── Agent Instance N
    ├── reviewer              (depends on research artifacts)
    └── synthesizer           (depends on accepted findings)
        └── verified outcome

Agent Definition 是可版本化定义，Binding Snapshot 固定本次模型、权限、Skill、Tool 与 Reality 边界，Instance 是实例身份，Run 是一次执行记录。同一定义可以并行实例化多次，但权限只能从 Session 上限继续收窄。

团队不是固定模板的硬编码分支

模板提供可理解的协作规约和默认角色，模型仍可依据目标建议人数、角色和依赖；Runtime 负责验证资源、权限、图结构和完成合同。

运行中连续输入

运行中的新消息先进入 Turn Inbox，不直接修改正在提交副作用的节点。Input Classifier 结合当前安全点、目标关系和执行状态，将消息分为本轮补充、下一安全点重规划、新 Task、旁支 Task、取消或仅排队。

输入关系处理约束
补充当前目标在下一安全点加入当前执行上下文不重复已提交副作用
改变方向生成 replan revision保留旧图证据与取消原因
独立新目标创建 Root Task，可继续同一 Session不混入原任务上下文
取消或停止传播取消信号并完成终态提交保存已完成证据

模型自主性与内核不变量

模型可以提议

任务关系、执行模式、团队拓扑、Agent 角色、工具意图、重规划、置信度与完成解释。

Runtime 必须决定

真实身份、授权、审批、并发准入、依赖、租约、幂等、事务、取消、恢复和终态提交。

Surface 只负责

展示投影、收集输入、发起命令、呈现审批与证据，不依据文本猜测运行关系。

性能与可靠性设计

  • 活动执行以内存热状态为读取与调度权威，事件账本异步持久化并支持重建。
  • Provider 容量按进程、账号、模型和 token 压力统一准入，并为交互请求保留容量。
  • 工具按副作用、依赖和资源键分批；独立幂等调用并行，写操作按资源有序。
  • 工具调用在执行前按注册 schema 校验参数；失败协议会终止悬挂预执行，早启动活动会立即进入 canonical projection。
  • Session 历史采用不可变分块、热尾段和请求编译缓存；完整历史仍耐久保存。
  • 长时间 Provider/Tool await 不应持有全局或 Session 写锁。
