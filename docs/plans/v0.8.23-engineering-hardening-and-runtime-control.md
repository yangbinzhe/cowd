# v0.8.23 Engineering Hardening and Runtime Control Plan

Status: active
Current implementation version: 0.8.72
Branch: develop
Merge policy: merge to master only after the v0.8.23 stage is accepted.

## Goals

v0.8.23 focuses on making the current AI runtime usable as an installable, observable, and controllable product baseline without weakening the existing session, memory, context, agent, channel, TUI, or WebUI work.

The release must improve:

- Installability: built artifacts must contain only required runtime assets and must run outside the source tree.
- Stability: one broken optional capability must not crash the whole daemon.
- Operability: logs, tests, release gates, and runtime diagnostics must expose enough signal for real usage.
- Architecture clarity: large gateway/API/control modules must start moving toward explicit bounded capabilities.
- Control consistency: channel/service permission, session, memory, context, agent, and task controls must align around one runtime control plane.

## Phase 1: Packaging and Runtime Asset Hygiene

Problems:

- `cowd-cli` build currently copies the whole `webui/` directory, including `node_modules`, into generated static assets.
- The daemon serves `current_dir()/webui`, so an installed binary can fail if launched outside the repository.
- Build script errors are silently ignored in several places, making damaged artifacts hard to diagnose.

Implementation:

- Copy only WebUI runtime assets: HTML, CSS, JS runtime modules, manifest, service worker, and assets.
- Exclude tests, Playwright/Vitest configs, package files, lockfiles, and `node_modules`.
- Resolve WebUI at runtime in this order:
  1. `COWD_WEBUI_DIR` when it points to a valid `index.html`.
  2. `./webui` for source-tree development.
  3. `<binary-dir>/webui` for installed binaries.
  4. fallback path with warning instead of panic.
- Remove `unwrap()` from this path.

Acceptance:

- `cargo build -p cowd-cli` creates `target/<profile>/webui/index.html`.
- Generated WebUI artifact does not contain `node_modules` or test files.
- Daemon startup does not panic when current working directory is not the repository.

## Phase 2: Build and Test Gate Correctness

Problems:

- `make test` and `make test-config` target `cargo test -p config`, but there is no `config` package.
- Release confidence is reduced when documented local gates are broken.

Implementation:

- Retarget config smoke tests to the actual package that owns configuration/runtime behavior.
- Keep OOM-safe job controls.
- Preserve full-install default; split build tiers remain a later release item.
- Extend the lightweight default gate so `make test` covers both runtime configuration behavior and CLI logging startup/retention smoke tests.

Acceptance:

- `make test-config` runs successfully.
- `make test` is a valid lightweight default test target.

Implemented in this stage:

- Corrected `make test-config` to run the runtime crate configuration tests instead of the removed `config` package target.
- Expanded `make test` into a valid lightweight gate covering runtime configuration and `cowd-cli` logging smoke tests with the existing safe test-thread control.
- Revalidated `scripts/release_gate.sh` as the full release gate and fixed the stale resume-latest assertion it exposed: DB-backed resumed status now reports the selected session id and SQLite session store instead of depending on legacy JSONL paths.

## Phase 3: Logging and Diagnostics

Problems:

- Daily logs can grow very large.
- Debug and release modes have different defaults but no retention or structured logging option.

Implementation:

- Add retention/rotation controls through environment or config.
- Add optional JSON log mode for service deployment and audit.
- Keep terminal output quiet by default in release.
- Add startup diagnostics for WebUI path, config home, platform registration, and database paths without leaking secrets.
- Make logger initialization idempotent so tests or embedding hosts that already installed a tracing subscriber do not crash the process.

Acceptance:

- Long-running daemon has bounded log growth.
- Debug issue reports can be collected without manual filesystem guessing.

Implemented in this stage:

- Switched logging initialization to `try_init()` and exposed whether this process installed the subscriber, preventing duplicate-initialization panic while keeping the startup log event observable.
- Added structured daemon startup diagnostics covering HTTP address, Unix socket path, workspace root, config home, WebUI path/availability, memory enablement/availability, unified session store availability, runtime config presence, auth requirement, CORS origin count, platform counts, platform types, platform setting keys, and message mirror configuration.
- Kept startup diagnostics secret-safe: platform setting values and auth token values are not serialized or logged.
- Reused the resolved WebUI path for both diagnostics and static serving so diagnostics reflect the actual serving path.
- Preserved non-fatal degraded startup behavior: missing WebUI still warns and falls back, missing memory manager remains `memory_available=false` instead of crashing.

## Phase 5: Runtime Control Plane Alignment

Problems:

- Session, memory, context, task, agent, channel, service, and approval controls exist but are not yet exposed as one coherent runtime kernel.

Implementation:

- Define a lightweight control-plane model:
  - identity
  - capability
  - permission
  - audit event
  - session binding
  - memory/context scope
  - channel/service adapter boundary
- Keep channels and services loosely coupled through permission-checked runtime operations.
- Add WebUI/TUI management surfaces only after backend contracts are stable.

Acceptance:

- Cross-channel operation can be reasoned about through a single permission/audit path.
- UI can explain who did what, through which channel, under which grant.

## Phase 6: Session Storage and Legacy JSONL Removal Audit

Problems:

- The current design direction is DB-first session infrastructure.
- Legacy JSONL should remain only as passive import material, not active runtime storage or automatic startup import.

Implementation:

- Audit remaining JSONL active paths.
- Remove active JSONL writes/reads from runtime flow.
- Keep explicit user-triggered import.
- Ensure failure to import old local files cannot block startup.

Acceptance:

- New sessions use DB-backed infrastructure only.
- Local legacy files are detected and reported as importable, not automatically loaded.

Implemented in this stage:

## Phase 7: Configuration and Runtime Provider Control

Problems:

- Provider configuration was previously initialized as a one-time immutable process snapshot.
- Tests and future daemon config reloads could be blocked by whichever code path first touched provider resolution.
- This weakens the broader configuration-control objective: model/provider selection should be explicit, inspectable, and reloadable without hidden global state ordering.

Implementation:

- Keep lazy provider loading from `~/.cowd/config.yaml` for default startup behavior.
- Allow explicit `init_global_providers()` calls to replace the in-memory provider snapshot.
- Return owned provider/model data from registry lookups so callers do not hold references across registry locks.
- Keep runtime client construction unchanged at the behavior boundary: clients still build from resolved provider config and fail clearly when no provider owns the requested model.

Acceptance:

- Runtime provider tests do not depend on local user config or test execution order.
- Future config reload can update provider/model routing in process.
- Existing model status and provider client construction continue to compile and run.

Implemented in this stage:

- Reworked `runtime::provider_registry` around `OnceLock<RwLock<ProvidersConfig>>` with explicit replacement semantics.
- Updated tools and CLI runtime provider client construction to borrow the owned resolved config at construction time.
- Added a protected runtime provider reload endpoint. `POST /api/runtime/providers/reload` reloads the merged runtime configuration into the global provider registry, returns a secret-safe provider/model routing summary, and skips replacement when configuration parsing fails. WebUI Runtime Console now exposes a compact provider reload action next to provider/model/route diagnostics.
- Aligned TUI Runtime Activity with the runtime provider control plane. The panel now shows provider registry status, provider/model counts, current model route resolution, and provider names from the same global registry used by execution and API control surfaces; Kernel health now degrades when the active model cannot resolve to a configured provider.
- Added TUI provider reload control through the command palette action model. The action reloads providers from the merged runtime config, updates the same global registry used by execution, shows success/warning/error feedback through TUI notifications and toasts, preserves the previous registry on config parse failure, and keeps API keys out of user-visible messages.
- Verified `gateway::tests::*`, `api_routes::tests::*`, WebUI module tests, and `cowd-cli` build.
