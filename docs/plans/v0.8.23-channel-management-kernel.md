# Cowd v0.8.23 Channel Management Kernel Plan

## 目标

v0.8.23 建立统一渠道管理应用体系。重点不是新增大量平台，而是把现有
Feishu、WeCom/WeChat、Email 三类渠道做深、做稳、做成可配置、可观测、
可审计、可恢复、可被 Agent 正确调度的企业级入口。

参考 `agents/hermes-agent` 后，本版本吸收的核心机制是：

- 平台注册元数据：平台不只是 adapter，而是带能力、配置、鉴权、限制、
  提示词、投递能力的完整 channel entry。
- Channel Directory：统一保存可触达的群、私聊、主题、邮箱联系人和最近会话。
- Delivery Router：统一解析 `origin`、`local`、`platform`、
  `platform:chat_id[:thread_id]` 等目标，不让每个 adapter 各自实现投递策略。
- Session Context：每条入站消息都带独立的 platform/chat/thread/user/message
  上下文，避免并发请求互相污染。
- Gateway Recovery：平台启动、连接、断线、限流、发送失败都投影为可查询健康状态。

Cowd 当前已有 `PlatformAdapter`、`PlatformRuntime`、Feishu、WeCom/WeChat、
Email、dedup、TUI/WebUI Gateway 面板雏形，但缺少统一的渠道管理内核。
v0.8.23 将在现有 Rust 架构内补齐这层，不引入独立外部 gateway。

## OpenClaw / Hermes 调研后的架构修订

本轮补充调研 `agents/openclaw` 与 `agents/hermes-agent` 后，结论是 Cowd
不能只建设“渠道层”，还必须同时明确“服务能力层”。飞书的 IM、卡片、
reaction、群聊目录属于 channel；飞书文档、云盘、知识库、多维表格、权限
属于 workspace service。两者可以使用同一个飞书应用账号和密钥，但不应该
在架构上混成一个 adapter。

### 可借鉴点

OpenClaw 飞书扩展的强点：

- Core 保持 plugin-agnostic，channel plugin 只处理 transport、presentation、
  callback envelope，不拥有产品命令树和策略。
- Feishu 扩展包内部已经分离 channel runtime 与 tool families：
  `doc`、`drive`、`wiki`、`bitable/base`、`perm`、`scopes`。
- Tool account 有明确选择顺序：显式 `accountId` 优先，其次 agent/context
  默认账号，再次配置默认账号。
- Secret contract 显式描述密钥目标、启用条件、配置/审计 surface。
- `perm` 默认禁用，其他读写工具族可配置启用，体现敏感能力默认收敛。
- Feishu bitable 能处理 `/base/` 与 `/wiki/` URL，并在 wiki 场景下解析
  node token 到真实 app token，这是资源服务能力，不是消息通道能力。

Hermes 的强点：

- `PlatformEntry` 把平台元数据、工厂、依赖、配置校验、env bridge、发送限制、
  LLM platform hint、standalone sender 放到 registry。
- `ChannelDirectory` 把 adapter 可枚举目标与历史 session 合并为可触达目录。
- `DeliveryRouter` 统一 `origin`、`local`、`platform:chat[:thread]` 投递。
- `session_context` 使用 task-local context，避免并发消息污染全局环境。

Cowd 当前短板：

- `PlatformAdapter` 仍然是消息收发 trait，缺少 channel entry、capability
  registry、directory、delivery target、service connector。
- Feishu 文档/知识库/多维表格这类操作没有统一归属；如果直接挂在平台
  adapter 上，会导致未来腾讯文档、金山文档、Notion、GitHub 等服务全部
  被错误理解为“渠道”。
- WebUI/TUI 目前只能呈现平台健康雏形，无法呈现账号、scope、工具族、资源、
  审计、降级状态。

## 最终目标架构：Channel Plane + Service Plane + Account Plane

```text
ProviderAccount(feishu-main)
  ├─ ChannelBinding(feishu.im)
  │    ├─ inbound events
  │    ├─ outbound delivery
  │    ├─ cards / reactions / thread replies
  │    └─ ChannelDirectory
  └─ ServiceBindings
       ├─ feishu.docx
       ├─ feishu.drive
       ├─ feishu.wiki
       ├─ feishu.bitable
       └─ feishu.permission

Agent / Task / Session
  ├─ ChannelContext: user talks from where, reply to where
  ├─ ServiceContext: what external resources can be operated
  ├─ PolicyContext: who can do what with which approval
  └─ AuditContext: every channel event and service action is traceable
```

核心判断：

- Channel Plane 回答：用户从哪里进入，Cowd 如何收到消息，如何回复。
- Service Plane 回答：Cowd 可以操作哪些外部系统、资源和 API。
- Account Plane 回答：这些能力使用哪个租户、账号、密钥、scope、策略。

飞书 key 是 `ProviderAccount` 的凭据。它可以同时授权 `feishu.im` channel
和 `feishu.docx/drive/wiki/bitable` service，但 service 不因此成为 channel
的内生能力。它们是同一 provider account 下的兄弟能力。

## 融合原则：在价值链融合，在代码边界隔离

本版本的目标不是把 OpenClaw、Hermes 的能力复制进 Cowd，也不是让 channel、
service、memory、context、agent 互相直接调用。正确融合方式是：

- Channel 提供“人和系统如何对话”的事实。
- Service 提供“系统可以操作什么外部资源”的事实。
- Account 提供“使用哪个身份和权限”的事实。
- Session 承接“这次互动属于哪条连续生命线”。
- Context 承接“当前推理需要看到哪些稳定事实和动态事实”。
- Memory 承接“哪些事实需要成为长期知识、资源索引或未来可召回依据”。
- Agent 承接“哪些能力可以被调度、委托、并行协作”。
- RuntimeEvent 承接“发生过什么、是否成功、如何审计和恢复”。

因此融合发生在 `CapabilityManifest`、`RuntimeEvent`、`ContextItem`、
`ExternalResourceRef`、`SessionBinding` 这些稳定契约上；各模块只消费契约，
不跨层依赖彼此内部实现。

### 与 Cowd 现有能力的对齐方式

#### Session

现有 `SessionLifecycleManager` 已经负责 TTL、idle、eviction、close。
v0.8.23 不替换它，只增加 channel/service 绑定事实：

- `ChannelIdentity -> session_id`
- `ExternalResourceRef -> session_id/task_id`
- `origin_delivery_target -> session_id`
- `last_channel_activity`
- `last_service_action`

Session 不需要知道 Feishu SDK、Email IMAP、Bitable API。它只保存绑定关系和
生命周期状态。

#### Context

现有 `context_runtime` 已经有 `StableHead`、`RuntimeHeader`、`Memory`、
`ToolTrace`、`Workspace`、`AgentPeer` 等 source，并且强调 prompt-cache
友好。渠道和服务能力应作为 context 的稳定事实进入头部，而不是把完整配置
或大资源正文塞入上下文。

稳定头部建议注入：

- 当前 `ChannelIdentity` 摘要。
- 当前 `ProviderAccount` 的非敏感标识、可用 capability family。
- 当前用户/群可用工具族和审批要求。
- 默认 reply target 与 home target。

动态区只注入：

- 当前任务相关的 `ExternalResourceRef`。
- ResourceDirectory 命中的摘要片段。
- 最近 service action 的结果摘要。
- 降级、限流、权限缺失等 warning。

这样既能发挥渠道/服务能力，又保持 KV cache 稳定。

#### Memory

现有 memory 已有 L0-L4、`MemoryKernel`、`MemoryTurnContext`、runtime event、
session store、hybrid search、maintenance、memory pulse。ResourceDirectory
不应该替代 memory，而是给 memory 提供外部资源的“权威索引层”。

写入规则：

- 原始文档、表格、大文件不直接写入 memory。
- memory 保存资源摘要、结构化事实、决策、冲突、权威引用。
- `ExternalResourceRef` 是 memory entry 的 evidence/ref。
- 文档更新、表格变更、评论事件触发 memory maintenance candidate。
- 长期知识进入 L2/L3/L4；会话临时资源只绑定 session。

这样能让 memory “知道哪里有知识”，而不是被大型资源拖垮。

#### Agent / Multi-Agent

现有 `agent_collaboration` 已有 work graph、wave dispatch、review packet、
scorecard、memory pulse。渠道和服务能力应成为 agent 调度的 capability
输入，而不是每个 agent 自行理解平台细节。

Agent 只看到：

- `CapabilityManifest`
- `AllowedServiceAction`
- `ResourceRef`
- `PolicyRequirement`
- `DeliveryTarget`

多 agent 协作时：

- Planner 根据任务和资源 refs 选择服务能力。
- Researcher 可读 doc/wiki/drive/base。
- Executor 可写 doc/base 或发送 channel reply。
- Reviewer 检查 service action audit、resource diff、memory candidate。
- Coordinator 只通过 DeliveryRouter 对外输出。

这能让多 agent 发挥 1+1>2：分工围绕能力和证据，不围绕平台 SDK。

#### RuntimeEvent

现有 `CowdEvent` 和 memory runtime event 是全局观测基础。渠道与服务不应各写
各的日志格式，而应统一投影事件：

- `channel.inbound.received`
- `channel.outbound.sent`
- `channel.outbound.failed`
- `channel.directory.refreshed`
- `service.account.probed`
- `service.tool.invoked`
- `service.tool.failed`
- `service.resource.discovered`
- `service.resource.indexed`
- `service.permission.degraded`

UI、审计、恢复、测试都读事件投影，不直接扫描 adapter 内部状态。

### 不互相浸入的边界规则

- ChannelConnector 不调用 MemoryKernel，只发 envelope/event。
- ServiceConnector 不调用 SessionLifecycleManager，只接收 actor/account/resource
  上下文并返回 action result。
- Memory 不调用外部 API，只保存 ref、摘要、事实、索引状态；资源刷新由
  ServiceConnector 或 background resource indexer 执行。
- Context 不执行工具，只选择和编排要注入的事实。
- Agent 不持有密钥，不直接使用 provider SDK，只通过 service tool registry。
- UI 不绕过 registry 直接操作 adapter/service，只调用管理 API。

### 最小高价值闭环

首轮实现不追求“大而全”，必须先打通这条闭环：

```text
Inbound ChannelEnvelope
  -> ChannelIdentity binds Session
  -> Context stable head gets channel/account/capability summary
  -> Agent selects ServiceConnector by CapabilityManifest
  -> Service action returns ResourceRef + ActionResult
  -> RuntimeEvent records audit
  -> Memory receives summary/evidence candidate
  -> DeliveryRouter replies to origin/home/channel target
  -> WebUI/TUI shows channel/service/resource/audit state
```

这个闭环能够充分发挥现有 session、context、memory、agent、event、TUI/WebUI
能力，同时保持 OpenClaw/Hermes 借鉴能力以插件化、契约化方式进入 Cowd。

## 身份、权限与审批控制

跨渠道、跨服务能力必须建立在统一身份和策略层上。设计目标是：

- 默认安全：未知渠道用户没有跨服务权限。
- 可渐进放权：支持管理员配置、用户申请、一次性确认、长期授权。
- 可解释：每次允许/拒绝都能说明原因。
- 可审计：所有跨渠道、跨服务 action 都有 actor、source、target、resource、
  account、policy、approval 记录。
- 可撤销：长期授权、同权绑定、目标白名单都可以失效或人工撤销。

### Identity Graph

建立统一身份图谱，不把微信用户、飞书用户、邮箱用户、本地 TUI 用户看成
完全独立实体，也不默认看成同一人。

```text
Principal(user:yi)
  ├─ ChannelIdentity(feishu:user_open_id)
  ├─ ChannelIdentity(wechat:union_id/open_id)
  ├─ ContactIdentity(email:yi@example.com)
  ├─ LocalIdentity(tui:local_user)
  └─ VerifiedAttributes
       ├─ phone_hash
       ├─ email_hash
       └─ organization_id
```

身份关系分三种可信度：

- `verified`: 已验证同一人，可同权。
- `claimed`: 用户声称或系统推断，需要确认。
- `observed`: 系统看到手机号/邮箱/姓名相似，只能作为申请提示，不能自动授权。

手机号、邮箱等敏感字段只保存 hash 或受保护 secret ref。UI 可以展示脱敏值。

### 同权策略

支持三种模式：

#### 1. Strict

默认企业安全模式。

- 不自动同权。
- 只有管理员显式绑定或用户完成双端验证后才同权。
- 适合生产环境。

#### 2. Verified Attribute Match

中等自动化模式。

- 当两个渠道都能提供已验证手机号或已验证邮箱，且 hash 匹配，可以自动生成
  `claimed` 绑定。
- 是否直接升级为 `verified` 由策略决定。
- 可配置需要用户在两个渠道分别确认。

#### 3. Admin / User Requested Equivalence

灵活模式。

- 用户可在微信里申请“绑定我的飞书身份”。
- 系统生成一次性确认码或飞书确认卡片。
- 双端确认后升级为 `verified`。
- 管理员也可直接绑定或撤销。

配置示例：

```toml
[identity.equivalence]
default_mode = "strict" # strict | verified_attribute_match | user_requested
auto_verify_email_hash = false
auto_verify_phone_hash = false
require_dual_channel_confirm = true
binding_ttl_days = 365
allow_admin_override = true
```

### Policy Decision 输入

每次跨平面动作都生成 `CrossPlaneAction`，再进入 policy engine。

```text
CrossPlaneAction
  actor_principal
  source_channel
  session_id
  requested_capability
  provider_account
  target_ref
  resource_ref
  risk_level
  data_classification
```

PolicyDecision 输出：

- `allow`
- `deny`
- `require_single_approval`
- `require_persistent_grant`
- `require_admin_approval`
- `degrade`

拒绝或降级必须返回可读原因，例如：

- `unknown_actor`
- `unverified_identity_equivalence`
- `capability_not_granted`
- `target_not_allowlisted`
- `resource_not_allowlisted`
- `provider_scope_missing`
- `sensitive_export_requires_approval`
- `channel_cannot_deliver_file`

### 权限粒度

权限必须支持多层组合，不能只用简单 allow/deny。

#### Capability 粒度

示例：

- `channel.feishu.send_text`
- `channel.feishu.send_image`
- `channel.feishu.send_file`
- `service.feishu.docx.read`
- `service.feishu.docx.export`
- `service.feishu.drive.download`
- `service.feishu.bitable.read`
- `service.feishu.bitable.write`
- `service.feishu.permission.modify`

#### Target 粒度

示例：

- 允许发到某个飞书群。
- 允许回源回复，但不允许主动发到其他群。
- 允许发 Email digest，但不允许发附件。

#### Resource 粒度

示例：

- 允许读取某个 wiki space。
- 允许读取某个 docx。
- 允许写入某个 bitable app/table。
- 禁止下载包含敏感标签的文件。

#### Data 粒度

示例：

- `public`
- `internal`
- `confidential`
- `secret`

不同数据等级对应不同审批要求。

### Grant 模型

授权不是只有一次性开关，需要支持多种生命周期。

```text
Grant
  principal_id
  capability
  account_id
  target_ref?
  resource_ref?
  source_channel?
  scope
  grant_type
  expires_at
  max_uses
  created_by
  approval_id
```

grant 类型：

- `single_use`: 单次授权，用完即失效。
- `session`: 当前 session 内有效。
- `task`: 当前 task/goal 内有效。
- `time_bound`: 指定时间内有效，如 24 小时、7 天。
- `persistent`: 长期有效，必须可撤销。
- `inherited`: 来自身份同权、角色、组织策略。

### 审批层级

建议默认审批策略：

```text
低风险
  - 回源回复文本
  - 查询已绑定 session 的公开资源摘要
  -> allow

中风险
  - 从微信读取飞书文档摘要
  - TUI 推送消息到已白名单飞书群
  -> session/task grant 或 single approval

高风险
  - 下载文件并跨渠道转发
  - 写多维表格
  - 主动群发
  -> single approval 或 time-bound grant

极高风险
  - 权限修改
  - 删除/覆盖外部资源
  - 导出敏感文件
  -> admin approval，默认不长期授权
```

### 配置示例

```toml
[policy.defaults]
unknown_actor = "deny"
unverified_equivalence = "require_dual_confirm"
cross_channel_file_transfer = "require_single_approval"
external_resource_write = "require_single_approval"
permission_modify = "require_admin_approval"

[[policy.grants]]
principal = "user:yi"
capability = "channel.feishu.send_text"
target = "channel://feishu/chat/oc_xxx"
grant_type = "persistent"

[[policy.grants]]
principal = "user:yi"
capability = "service.feishu.docx.read"
resource = "service://feishu/wiki/space_xxx"
grant_type = "time_bound"
ttl = "30d"

[[policy.grants]]
principal = "role:admin"
capability = "service.feishu.bitable.write"
resource = "service://feishu/bitable/app_xxx/table_xxx"
grant_type = "persistent"
requires_audit = true
```

### 典型场景

#### TUI 推送飞书图片

```text
actor = local:tui
capability = channel.feishu.send_image
target = channel://feishu/chat/oc_xxx
policy:
  - local:tui 是否绑定 Principal
  - Principal 是否有 send_image grant
  - target 是否 allowlisted
  - 图片路径是否在允许工作区
decision:
  allow / require approval / deny
```

#### 微信请求下载飞书文档并返回

```text
actor = wechat:user_x
source = channel://wechat/chat/x
capability = service.feishu.docx.export + channel.wechat.send_file
resource = service://feishu/docx/doc_x
policy:
  - wechat:user_x 是否与 Principal verified 绑定
  - Principal 是否可读/export 该 docx
  - 文件大小和分类是否允许跨渠道
  - 微信是否支持文件返回，否则 degrade 为摘要/链接
decision:
  require_single_approval 或 time_bound grant
```

#### 微信与飞书同手机号同权

```text
observed:
  feishu.phone_hash == wechat.phone_hash
policy:
  if auto_verify_phone_hash = false:
    create claimed equivalence
    ask user to confirm in both channels
  after confirmed:
    create Principal binding
    inherited grants become available
```

### UI / TUI 管理

WebUI 需要有：

- Identity Bindings：查看、确认、撤销跨渠道身份绑定。
- Grants：按用户、角色、能力、资源、目标查看授权。
- Approval Queue：单次授权、长期授权、管理员审批。
- Policy Simulator：输入 actor/action/resource/target，预览 allow/deny 原因。
- Audit Timeline：查看所有 policy decision 与 action result。

TUI 需要有：

- `/identity` 查看当前身份绑定。
- `/grant` 查看当前 session/task 的授权。
- `/approve` 处理待审批动作。
- `/policy test` 快速模拟权限判断。

## TUI / WebUI 权限与互操作管理分阶段方案

这部分必须做成管理面，而不是主对话主线的一部分。原则是所有 UI 只读写
`IdentityGraph`、`GrantStore`、`ApprovalQueue`、`AuditProjection`、
`CapabilityManifest`，不直接操作 channel adapter 或 service SDK。

### UI 信息架构

#### Overview

展示系统是否可安全互操作：

- 已启用 provider accounts。
- 已启用 channels。
- 已启用 service families。
- 已验证 principal 数。
- claimed/observed 待确认身份数。
- active grants 数。
- pending approvals 数。
- 最近跨平面 action 成功/失败数。

#### Identity Bindings

能力：

- 查看 Principal 与 Feishu/WeChat/Email/TUI identity 的绑定。
- 查看 trust：verified/claimed/observed/unknown。
- 发起双端确认。
- 管理员确认/撤销同权。
- 查看绑定来源：手机号 hash、邮箱 hash、管理员、用户申请、历史导入。

#### Grants

能力：

- 按 principal、role、capability、target、resource、account 筛选。
- 创建 single/session/task/time_bound/persistent grant。
- 暂停、撤销、延长授权。
- 查看授权来源和审批记录。
- 显示 grant 将影响哪些跨渠道动作。

#### Policy Simulator

能力：

- 输入 actor、source channel、capability、resource、target、risk、data class。
- 返回 allow/deny/approval/degrade。
- 显示命中 grant 或拒绝原因。
- 显示如果要放行，需要创建哪类 grant。

#### Approval Queue

能力：

- 单次授权。
- 当前 session/task 授权。

## 与 Agent / Session / Memory / Context 的关系

Agent 不应该感知底层 adapter 细节，只接收稳定事实：

- 当前会话来自哪个 `ChannelIdentity`。
- 默认回复目标是什么。
- 当前用户/群允许哪些 service capability。
- 当前任务相关的 `ExternalResourceRef` 有哪些。
- 哪些操作需要审批。

Session 负责连续性：

- ChannelIdentity 绑定 session。
- Service action 绑定 task/session。
- ResourceDirectory 中的资源可被 session 引用、恢复、继续操作。

Memory 负责长期知识：

- 外部资源只存权威引用、摘要、索引状态和必要结构化事实。
- 大型文档/表格进入 ResourceDirectory + Memory index，不进入完整运行态。
- 资源更新事件触发增量索引和冲突检测。

Context 负责运行态注入：

- 稳定头部保留 provider/account/capability/policy 摘要，提升 KV cache 命中。
- 动态区只注入与任务最相关的资源片段、目录节点和操作结果。
