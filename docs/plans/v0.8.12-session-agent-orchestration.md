# v0.8.12 Session-Agent Orchestration Plan

## Version Goal

v0.8.12 的核心目标是把 Cowd 从“可用的单会话 AI 工具”推进到“会话驱动的多 agent 协同工作平台”。

重点不再是补散点能力，而是统一以下五条主线：

- 会话全生命周期：创建、激活、运行、暂停、接续、分叉、压缩、归档、删除、恢复。
- 多 agent 协同：分解、派发、并行、沟通、冲突解决、综合验收。
- 任务调度：task phase、wave、team、worker、cron、yolo/solo 连续执行的统一调度。
- 事件与存储：hot runtime、cold store、event bus、SQLite、memory 的一致性。SQLite/DB 是唯一会话事实源。
- 交互呈现：TUI/WebUI/API 对同一 session/task/agent 状态使用同一 DTO 和同一时间线。

## Current Reality

已经具备的基础：

- `SessionKernel` 已经统一持有：
  - active runtime registry
  - `UnifiedSessionStore`
  - `SessionEventBus`
- `ConversationRuntime` 已经存在：
  - session store dual-write
  - event log
  - SSE callback
  - collaboration orchestrator slot
  - discussion engine slot
  - tool concurrency semaphores
  - cancellation token
- multi-agent 相关能力已存在但未形成产品闭环：
  - `SubAgentRuntime`
  - `CollaborationOrchestrator`
  - `DiscussionEngine`
  - `TeamRegistry`
  - `Agent` tool manifest/output persistence
  - wave orchestrator / lane completion
- v0.8.9-v0.8.11 已经补齐 session persistence、task phase cockpit、WebUI live workbench、memory explain、工具 parity contract。

主要缺口：

- SessionKernel 仍偏 accessor，不是完整生命周期服务。
- API/TUI/daemon/CLI 仍有局部路径直接处理 session/runtime/store 细节。
- agent job 与 parent session 缺少统一 trace/span/event 关系。
- 多 agent 沟通、结果归并、冲突解决未进入稳定可观测时间线。
- team/wave/worker/task phase/session 之间缺少统一调度模型。
- 会话恢复能恢复消息和 metadata，但不能完整恢复 agent task graph、in-flight 状态、协同上下文。
- WebUI/TUI 还不能以“任务 cockpit”方式展示多 agent 并行执行、阻塞、交接、评审。
- JSONL 历史链路仍残留在 CLI/runtime 文案和兼容逻辑里。v0.8.12 必须坚决改成 DB-first：
  - 不自动扫描或导入 JSONL。
  - 不把 JSONL 当运行态 session 主存储。
  - 不用本地 JSONL path 直接 resume。
  - 只允许用户显式 `import-session` 导入本地旧文件。
  - JSONL 仅作为导出、debug bundle、被动本地导入格式存在。

## Phase 1: SessionLifecycleKernel

### Objective

把 `SessionKernel` 从 accessor 升级为会话生命周期服务边界。所有入口通过它完成 session create/start/append/sync/pause/resume/fork/archive/delete。

### Design

新增或完善语义方法：

- `create_session(input) -> SessionEnvelope`
- `activate_session(session_id) -> RuntimeHandle`
- `append_user_message(session_id, message) -> MessageEnvelope`
- `run_turn(session_id, prompt, options) -> TurnEnvelope`
- `pause_session(session_id, reason)`
- `resume_session(session_id, mode)`
- `fork_session(session_id, from_sequence, options)`
- `archive_session(session_id)`
- `delete_session(session_id, scope)`
- `session_snapshot(session_id) -> SessionSnapshot`

统一 DTO：

- `SessionEnvelope`
- `MessageEnvelope`
- `TurnEnvelope`
- `SessionSnapshot`
- `SessionLifecycleEvent`

### TDD First

Red tests：

```bash
cargo test -p cowd-cli session_kernel_lifecycle_create_activate_resume -- --nocapture
cargo test -p cowd-cli session_kernel_fork_preserves_lineage -- --nocapture
cargo test -p cowd-cli session_kernel_delete_cleans_hot_and_cold_state -- --nocapture
```

Acceptance：

- 新会话同时创建 hot runtime 和 cold record。
- resume 冷会话时能 lazy hydrate snapshot。
- fork 后 parent/child lineage 可查询。
- delete 明确支持 active-only、cold-only、all 三种语义。
- API 主路径不再直接操作 `ActiveSessions`。

## Phase 1A: DB-First Session Store, No Automatic JSONL Import

### Objective

把 session 管理从旧文件习惯中彻底切出来。DB 是唯一运行态事实源；JSONL 不再自动导入、不再自动保存、不再直接 resume。

### Design

新的边界：

- `UnifiedSessionStore` / `SessionKernel` 是 canonical store。
- `SessionHandle.path` 不再代表主 session 文件；主身份是 `session_id`。
- CLI/TUI/daemon/API 运行态不得设置 JSONL persistence path。
- 本地 `.jsonl/.json` 只通过被动发现提醒用户。
- 显式导入入口：`cowd import-session <path>`。
- 显式导出入口：继续保留 `cowd export --format jsonl` 或等价导出能力。

禁止行为：

- 启动时扫描并自动导入 JSONL。
- `/resume local.jsonl` 直接恢复。
- `latest` 读取本地文件目录。
- turn append 自动写 `.cowd/sessions/<id>.jsonl`。
- 因单个本地文件解析失败阻塞 DB session store 初始化。

### TDD First

```bash
cargo test -p cowd-cli managed_sessions_default_to_sqlite_and_detect_legacy_imports -- --nocapture
cargo test -p cowd-cli load_session_reference_rejects_unimported_local_session_file -- --nocapture
cargo test -p cowd-cli help_mentions_db_resume_and_explicit_import -- --nocapture
cargo test -p cowd-memory store::session::tests -- --nocapture
```

### Acceptance

- `get_unified_store()` 不触发 JSONL migration。
- 新 CLI/TUI session 不创建 JSONL 文件。
- `/session list` 显示 SQLite store，并被动提示本地 legacy 文件数量。
- `cowd import-session <path>` 能导入指定本地文件。
- 旧 DB 缺少 `input_tokens/output_tokens/estimated_cost_usd/status` 时自动补 schema。
- 本地旧文件损坏不影响 DB store 初始化。

## Phase 2: Unified Event Timeline

### Objective

建立全平台统一时间线。session、task、phase、agent、tool、memory、approval、discussion、scheduler 全部写入同一种 event envelope。

### Design

统一事件格式：

```json
{
  "event_id": "...",
  "session_id": "...",
  "scope": "session|task|agent|tool|memory|approval|scheduler",
  "type": "...",
  "sequence": 42,
  "parent_id": "...",
  "span_id": "...",
  "correlation_id": "...",
  "created_at_ms": 0,
  "payload": {}
}
```

需要合并的现状：

- `message_appended`
- `/api/sessions/:id/events`
- `TaskPhaseArtifact`
- agent manifest status
- tool start/finish
- memory audit
- approval gate events
- discussion contributions

### TDD First

```bash
cargo test -p cowd-cli session_timeline_orders_cross_scope_events -- --nocapture
cargo test -p cowd-cli session_timeline_links_agent_tool_and_task_spans -- --nocapture
cargo test -p cowd-cli session_timeline_rebuilds_snapshot_after_restart -- --nocapture
```

Acceptance：

- API/TUI/WebUI 使用同一 timeline DTO。
- session refresh 后 timeline 顺序稳定。
- agent/tool/task event 可以通过 `parent_id/span_id` 追溯。
- SQLite event index 支持 session_id + sequence 分页。

## Phase 4: Multi-Agent Wave Scheduler

### Objective

把已有 `CollaborationOrchestrator`、`WaveOrchestrator`、`TeamRegistry` 产品化为真实可调度的并行解决问题能力。

### Design

调度模型：

- `PlanGraph`: task -> phase -> wave -> agent run
- `Wave`: 可并行 agent run 集合
- `Dependency`: agent run 或 phase 依赖
- `JoinPolicy`: all_success / quorum / leader_decides / continue_on_failure
- `BudgetPolicy`: max_agents / max_parallel / max_tokens / max_time
- `FailurePolicy`: retry / reassign / escalate / block

调度 API：

- `POST /api/tasks/:id/plan`
- `POST /api/tasks/:id/waves`
- `POST /api/tasks/:id/waves/:wave_id/run`
- `GET /api/tasks/:id/orchestration`

### TDD First

```bash
cargo test -p runtime wave_scheduler_respects_dependencies_and_parallel_limits -- --nocapture
cargo test -p runtime wave_scheduler_reassigns_failed_agent_when_policy_allows -- --nocapture
cargo test -p cowd-cli task_orchestration_api_runs_two_parallel_agents -- --nocapture
```

Scenario tests：

```bash
scripts/agent_wave_scenario.sh
scripts/task_orchestration_db_audit.sh
```

Acceptance：

- 两个无依赖 agent 能并行执行。
- 有依赖 agent 必须等待上游完成。
- 失败 agent 进入 blocker/retry/reassign 流程。
- 所有 wave 状态可从 API/TUI/WebUI 查询。

## Phase 5: Agent Communication Protocol

### Objective

让 agent 能围绕任务共享上下文、提问、交接、质疑和达成共识，而不是只做并行孤岛。

### Design

新增协议对象：

- `AgentMessage`
- `AgentQuestion`
- `AgentHandoff`
- `AgentClaim`
- `AgentConflict`
- `AgentDecision`

通道：

- parent session timeline
- L4 team memory
- discussion engine
- task phase artifacts

关键规则：

- agent 之间默认不能直接写 L0/L1。
- 所有 cross-agent communication 必须写 event。
- claim/conflict 必须能被 review/fact-check 引用。
- leader synthesis 必须生成 final decision artifact。

### TDD First

```bash

cargo test -p runtime agent_claim_conflict_triggers_discussion_round -- --nocapture

```

Acceptance：

- 多 agent 贡献可见、可排序、可追溯。
- 冲突 claim 能触发 discussion。
- leader decision 进入 task phase review。
- WebUI/TUI 能展示 discussion summary。

- 10 agent runs with max_parallel=4.
- 10k timeline events paging p95.
- session resume after gateway restart.
- SQLite busy_timeout and write contention.

## Definition Of Done

v0.8.12 完成时必须满足：

- 会话生命周期只能通过统一 Kernel 主路径完成。
- 多 agent 运行必须能在 parent session timeline 中完整追踪。
- 任务拆解、wave 并行、agent handoff、review artifact 形成闭环。
- session resume 能恢复 task-agent graph。
- TUI/WebUI 都能看到同一 orchestration 状态。
- 所有新增能力有 TDD 单测、API contract test、tmux/browser/db scenario test。
- `make release-gate` 通过。
- 测试结束无 tmux/port/temp db 残留。

## Explicitly Deferred

- 第 7 项依用户要求暂不处理。
- 全仓格式化治理单独排期，不混入 v0.8.12 主线。
- 外部 plugin runtime parity 可作为 P2 插入，但不能阻塞 session-agent orchestration 主目标。
