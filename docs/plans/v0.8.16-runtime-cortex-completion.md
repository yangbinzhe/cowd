# Cowd v0.8.16 Runtime Cortex Completion Plan

## Version Goal

v0.8.15 established the Runtime Cortex spine and productized the validated spike
mechanisms:

- `ContextLeanProbe`
- RuntimeRun lightweight tree summary
- `CollaborationBoard`
- multi-agent scorecard
- MemoryPulse -> reviewable maintenance candidates
- WebUI/TUI Runtime Probe display

v0.8.16 must turn these mechanisms into durable, connected enterprise workflow.
The goal is not a broader platform. The goal is to close the remaining loops:

```text
RuntimeRun tree -> AgentTask -> CollaborationBoard
               -> MemoryMaintenanceQueue -> ContextPolicy
               -> WebUI/TUI cockpit -> Scenario gate
```

The version is complete only when the new runtime signals are persistent,
explainable, visible, tested, and useful under failure.

## Current State

Already completed in `develop`:

- `/api/context/current` returns `lean_probe`.
- WebUI Context and Runtime Console render `Runtime Probe`.
- TUI Runtime panel renders pressure level and degradation path.
- `/api/sessions/:id/runs` returns `tree.summary`.
- `CollaborationBoard::memory_maintenance_candidates()` converts conflicts and
  memory pulses into reviewable candidates.
- `scripts/v0815_eval.sh` validates the current foundation.

Remaining gaps:

- Memory maintenance queue is still in-process, not durable.
- Collaboration boards are not persisted or linked to parent RuntimeRun ids.
- Agent work has no first-class `AgentTask` lifecycle tied to runtime trace.
- `ContextLeanProbe` is diagnostic only; it does not yet guide context policy.
- WebUI/TUI display runtime signals but do not yet provide full drilldown.
- Browser/tmux scenario tests do not yet cover Runtime Probe, run tree, and
  collaboration memory pulse workflows.
- Large-state performance coverage is still partial.

## Design Principles

1. Persist facts, not implementation internals.
2. Keep hot paths bounded; heavy analysis is deferred.
3. Every auto-generated candidate remains reviewable.
4. RuntimeRun remains the trace spine.
5. Context policy can adapt only through explicit, testable rules.
6. UI consumes stable DTOs only.
7. Failures degrade locally and are visible.

## Phase 1: Durable Memory Maintenance Queue

### Objective

Make memory maintenance candidates survive restart and become a reliable part of
the memory lifecycle.

### Design

Add a persistent maintenance queue backed by SQLite/store infrastructure:

```text
memory_maintenance_candidates
  - id
  - kind
  - status
  - entry_ids_json
  - summary
  - reason
  - confidence
  - source
  - source_ref
  - created_at
  - updated_at
```

Source examples:

- `scan`
- `collaboration_board`
- `runtime_review`
- `manual`

The existing in-memory `MaintenanceQueue` can remain as an implementation detail
or test fallback, but production memory managers should prefer the durable queue.

### TDD

Red tests first:

```bash
cargo test -p cowd-memory durable_maintenance_queue_persists_candidates -- --nocapture
cargo test -p cowd-memory durable_maintenance_queue_transitions_status_after_reopen -- --nocapture
cargo test -p cowd-cli memory_maintenance_scan_survives_manager_reopen -- --nocapture
```

### Acceptance

- Candidates survive process restart.
- Status transitions persist.
- Listing is paged and filterable by status/kind/source.
- A corrupt candidate row is skipped or degraded without blocking memory.
- Existing maintenance API behavior remains compatible.

### Implementation Ledger

Status: implemented first durable cut.

- `MaintenanceQueue::open_sqlite()` creates `memory_maintenance_candidates`.
- `MaintenanceCandidate` now carries optional `source` and `source_ref`.
- Queue upsert/list/transition persist to SQLite when configured.
- `CognitiveContextManager` prefers the durable queue from
  `config.store.sqlite_path` and falls back to memory on open failure.
- API maintenance listing supports `source`.
- WebUI API wrapper passes `source`.
- Tests cover reopen persistence, status transition, API compatibility, and
  collaboration candidate compatibility.

## Phase 2: RuntimeRun Span Hardening

### Objective

Upgrade the current run tree summary into a durable span model without adopting a
heavy tracing stack.

### Design

Normalize RuntimeRun payloads:

```text
RuntimeRun
  - run_id
  - parent_run_id
  - kind
  - profile
  - status
  - summary
  - refs
  - started_at_ms
  - completed_at_ms
  - duration_ms
  - error
```

Kinds:

- `main_turn`
- `yolo_goal`
- `agent_task`
- `tool_call`
- `context_build`
- `memory_op`
- `review`

Keep event storage append-only. Tree summary is derived from events.

### TDD

```bash
cargo test -p cowd-cli runtime_run_tree_links_parent_child_spans -- --nocapture
cargo test -p cowd-cli runtime_run_completed_records_duration_and_refs -- --nocapture
cargo test -p cowd-cli runtime_run_child_failure_does_not_fail_parent_query -- --nocapture
```

### Acceptance

- Run query returns roots, children, summary, and latest status per span.
- Child failures are visible.
- Context envelope ids, evidence refs, memory candidate ids, and agent task ids
  can be attached as refs.
- Query remains paged and bounded.

### Implementation Ledger

Status: implemented first span hardening cut.

- RuntimeRun started/completed payloads include `kind`, `summary`,
  `started_at_ms`, and `refs`.
- Completed payloads include `completed_at_ms`, `duration_ms`, and
  context-envelope refs when available.
- Existing run tree summary remains backward-compatible with older run events.
- API tests cover span kind, timestamps, duration, refs, child failure, and tree
  summary.

## Phase 3: AgentTask And Collaboration Binding

### Objective

Make multi-agent work first-class and tied to RuntimeRun.

### Design

Introduce an `AgentTask` DTO and persistence path:

```text
AgentTask
  - task_id
  - parent_run_id
  - agent_run_id
  - role
  - objective
  - status
  - context_envelope_id
  - result_summary
  - evidence_refs
  - collaboration_board_id
  - confidence
  - conflicts
  - created_at_ms
  - updated_at_ms
```

Collaboration binding:

- `CollaborationBoard` receives a stable `board_id`.
- Board summary is stored as a session event or task artifact.
- `MemoryPulseCandidate` exports maintenance candidates with `source_ref`.
- Parent RuntimeRun refs include agent task ids and board ids.

### TDD

```bash
cargo test -p runtime collaboration_board_has_stable_review_payload -- --nocapture
cargo test -p cowd-cli agent_task_event_links_to_parent_runtime_run -- --nocapture
cargo test -p cowd-cli collaboration_memory_pulses_create_source_linked_candidates -- --nocapture
```

### Acceptance

- Agent task state can be queried without reading logs.
- Collaboration board can be traced back to parent run.
- Memory candidates created from collaboration include board/source refs.
- Agent failure is represented as local degraded state.

## Phase 4: Context Policy Autotuning

### Objective

Let `ContextLeanProbe` guide safe context policy decisions.

### Design

Add a small deterministic policy layer:

```text
ContextPolicyDecision
  - profile
  - pressure_level
  - degradation_path
  - action
  - reason
```

Allowed actions:

- `none`
- `trim_tool_trace`
- `summarize_evidence`
- `prefer_orientation_packet`
- `write_handoff`
- `recommend_session_boundary`

Policy does not mutate memory or session state silently. It emits recommendations
or chooses bounded lease changes.

### TDD

```bash
cargo test -p runtime context_policy_uses_probe_for_safe_degradation -- --nocapture
cargo test -p runtime yolo_policy_preserves_active_task_under_pressure -- --nocapture
cargo test -p runtime review_policy_prioritizes_evidence_refs -- --nocapture
```

### Acceptance

- Critical pressure yields deterministic degradation action.
- Stable Head remains unchanged by policy decisions.
- Yolo keeps active task context before low-priority peer packets.
- Review keeps evidence before broad memory context.

## Phase 5: Runtime Cockpit Drilldown

### Objective

Make WebUI/TUI operationally useful for the new runtime signals.

### WebUI Work

- RuntimeRun tree expandable rows.
- Click a run to see refs: context, evidence, memory candidates, agent tasks.
- Context Probe panel shows pressure level, fallback, cache hashes, selected and
  omitted counts.
- Memory maintenance items show source/source_ref.
- Collaboration board summary displays lift, complementarity, conflicts, memory
  pulses.

### TUI Work

- Runtime tab supports run tree selection.
- Context tab shows policy action and probe.
- Memory tab shows source-linked maintenance candidates.
- Agent/collaboration summary is visible without reading logs.

### TDD

```bash

cargo test -p cowd-cli tui::components::runtime_activity_panel -- --nocapture
cargo test -p cowd-cli tui::components::context_panel -- --nocapture
```

### Acceptance

- Users can trace a runtime run to context, evidence, memory, and agent state.
- Empty/degraded states are explicit.
- Large run lists do not render unbounded rows.

## Implementation Order

1. Durable memory maintenance queue.
2. RuntimeRun span normalization and refs.
3. AgentTask/CollaborationBoard binding.
4. Context policy autotuning.
5. WebUI/TUI drilldown.
6. Scenario/failure gate.
7. Large-state performance.

## Parallelizable Lanes

- Lane A: durable memory queue.
- Lane B: RuntimeRun span model.
- Lane C: AgentTask/collaboration binding.
- Lane D: WebUI/TUI cockpit.
- Lane E: scenario/performance scripts.

Dependency rules:

- UI consumes only stable API DTOs.
- AgentTask links to RuntimeRun before WebUI drilldown depends on it.
- Memory queue source refs land before collaboration pulses are wired to API.
- Context policy actions are tested before they can alter lease behavior.

## Completion Definition

v0.8.16 is complete when:

- maintenance candidates are durable and source-linked.
- RuntimeRun spans can explain parent/child work.
- agent tasks and collaboration boards are traceable.
- context policy uses probe data safely.
- WebUI/TUI can drill down through runtime state.
- `scripts/v0816_eval.sh` passes.
- large-state tests prove bounded performance.
- no scenario leaves ports, tmux sessions, or temp state behind.
