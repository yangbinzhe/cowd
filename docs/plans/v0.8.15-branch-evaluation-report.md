# v0.8.15 Branch Evaluation Report

## Branches

| Branch | Purpose | Result |
| --- | --- | --- |
| `release/v0.8.15-runtime-cortex` | product integration target | accepted as the v0.8.15 main line |
| `spike/v0.8.15-lean-runtime-core` | minimal runtime/context performance probe | merged |
| `spike/v0.8.15-high-capability-core` | high-capability agent/memory collaboration probe | merged |

## Decision Summary

Both spike branches produced mechanisms with positive value and bounded
complexity, so both were merged into the product branch.

The important result is not that one design beat the other. The useful result is
that the two experiments operate at different layers and are compatible:

- lean runtime probe strengthens observability, stability, and degradation
  decisions.
- high-capability collaboration scoring strengthens multi-agent synthesis and
  memory pulse candidate generation.

Together they support the unified Runtime Cortex plan without creating a heavy
platform or a fragmented architecture.

## Lean Runtime Core Evaluation

Merged commit: `3fbd6b0`

Accepted mechanisms:

- `ContextLeanProbe`
- `StableHeadComparison`
- context pressure level
- minimal degradation path classification
- `scripts/context_runtime_lean_spike.sh`

Why accepted:

- It is read-only and does not change prompt assembly, lease selection, provider
  behavior, or user-facing execution.
- It makes Stable Head reuse measurable.
- It gives WebUI/TUI/RuntimeRun a small summary object for context pressure and
  fallback state.
- It supports performance goals directly: stable head cache reuse, bounded
  pressure classification, and explicit degraded paths.

Risks:

- Probe values are currently diagnostic. They do not yet drive runtime policy.
- UI does not yet expose the probe as a first-class panel field.

Next product step:

- Attach lean probe summaries to context envelope API/RuntimeRun summaries.
- Surface cache reuse and degradation path in WebUI/TUI runtime cockpit.

## High Capability Core Evaluation

Merged commit: `bcbe6d8`

Accepted mechanisms:

- `CollaborationBoard`
- `SharedBoardEntry`
- `CollaborationScorecard`
- `MemoryPulseCandidate`
- multi-agent synthesis scorecard output

Why accepted:

- It makes multi-agent value measurable instead of assuming that more agents are
  automatically better.
- It separates collaboration synthesis from memory mutation.
- It produces reviewable memory pulse candidates instead of silently modifying
  memory.
- It can support producer/reviewer, parallel explore/reducer, and conflict
  surfacing with small data structures.

Risks:

- Current scoring is heuristic and should be treated as an operational signal,
  not a final truth metric.
- Memory pulse candidates are not yet connected to the durable memory
  maintenance queue.
- Agent task state is still not a full parent-linked product workflow.

Next product step:

- Convert collaboration memory pulse candidates into memory maintenance
  candidates.
- Link collaboration boards to parent RuntimeRun ids.
- Add UI presentation for collaboration score and conflicts.

## Final Architecture Judgment

The right v0.8.15 direction is a unified product branch, not competing product
forks.

The branch experiment proved that the two original design directions are not
opposites:

- the focused plan supplies the runtime spine.
- the high-capability plan supplies the intelligence mechanisms.

The product architecture should keep the focused spine and admit high-capability
mechanisms only when they remain explainable, bounded, and testable.
