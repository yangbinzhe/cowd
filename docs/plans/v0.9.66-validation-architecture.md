# v0.9.66 Validation Architecture

## Goals

- Keep Rust build artifacts off the Datas NTFS/FUSE mount by default.
- Provide fast, core, full, and live validation lanes with explicit scope.
- Reduce global-state race failures by serializing process-wide env mutation.
- Keep the current product surface intact while preparing `cowd-cli` for future crate/test-boundary extraction.

## Validation Lanes

| Lane | Entry | Purpose |
| --- | --- | --- |
| unit-fast | `scripts/validate.sh unit-fast` | quick edit feedback: formatting, small crates, memory tuner, worker-state env isolation, WebUI unit tests |
| contract | `scripts/validate.sh contract` | package/API/CLI contracts without browser or tmux scenarios |
| scenario | `scripts/validate.sh scenario` | one debug build plus daemon/TUI/WebUI runtime scenario scripts |
| release | `scripts/validate.sh release` | clean build, install, setup smoke, and minimal release smoke |

All active lanes use `scripts/validate.sh` and default to `/tmp/cowd-target-*` when `/tmp` has enough free space. The old `validate_fast/core/full/live`, `validate_segmented`, and `release_gate` scripts are compatibility wrappers.

## Current `cowd-cli` Boundary

`cowd-cli` remains the heaviest target because it owns:

- CLI parsing and command execution
- TUI state and rendering
- daemon/gateway/API routes
- session/resume/YOLO control
- runtime/provider bootstrap
- connector and memory surface projection

This version does not split crates yet. It reduces blast radius by:

- running full `cowd-cli` tests single-threaded in the full lane;
- providing a targeted `cowd-cli` gateway check in the core lane;
- keeping provider-registry tests serial where global provider state is mutated.

## Next Extraction Boundary

The first safe extraction should move testable logic behind library-facing modules before creating new crates:

1. Gateway/session registry tests stay isolated from provider bootstrap.
2. TUI projection/state tests avoid real daemon and provider state.
3. API route contract tests use explicit in-memory stores and config roots.
4. YOLO/resume/session tests use bounded timeouts and local test stores.

Only after those internal boundaries are stable should new crates such as `cowd-gateway`, `cowd-tui`, or `cowd-session` be introduced.
