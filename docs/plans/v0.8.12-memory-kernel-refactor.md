# v0.8.12 Memory Kernel Refactor

## Design Correction

The memory architecture must stay pure.

The target is not a stack of RAG, vector search, graph databases, wiki pages, snapshots, and agent notes.

The target is one coherent memory organism:

```text
Experience -> Trace -> Pattern -> Orientation -> Action -> Revision
```

Five memory layers remain valuable, but they are a governance structure. Trace / Pattern / Orientation is the runtime organization model.

This means:

- L0-L4 define authority, scope, and write rules.
- Trace/Pattern/Orientation defines how knowledge moves through the organism.
- Session and agent integration must go through one MemoryKernel, not direct ad-hoc calls.

## Core Principle

Cowd memory should not become smarter by keeping more active content.

It should become smarter by maintaining the shortest reliable path from current intent to valid orientation.

Large-scale memory is achieved by:

- preserving traces.
- organizing patterns.
- keeping orientation small and authoritative.
- making all cold knowledge reachable through paths.
- never deleting history just because it is no longer active.

## Five-Layer Governance Model

### L0: Constitution

Purpose:

- identity, system doctrine, protected constraints, human-defined or AI-established foundational rules.

Authority:

- user/system highest authority.
- AI may propose L0 changes, but cannot silently mutate protected L0.

Runtime role:

- Orientation.

Implementation:

- existing `MemoryLayer::L0`.
- write source limited by `MemoryWriteGuard`.
- explicit audit required for mutation.

Best mechanisms:

- deterministic storage.
- explicit versioning.
- no vector-only recall.
- direct pinning into context when enabled.

### L1: Core Instinct

Purpose:

- stable working preferences, default behavior, durable habits, model/session operating assumptions.

Authority:

- user explicit > repeated confirmed behavior > AI inference.

Runtime role:

- Orientation plus high-confidence Pattern.

Implementation:

- existing `MemoryLayer::L1`.
- short TTL cache is valid, but entries must still carry source and state.

Best mechanisms:

- preference extraction.
- reinforcement scoring.
- bounded active cache.
- user correction supersession.

### L2: Project Mind

Purpose:

- project conventions, architecture, code symbols, tests, current requirements, project-specific decisions.

Authority:

- repository facts and tests > project decisions > tool observations > assistant inference.

Runtime role:

- Pattern and Orientation.

Implementation:

- existing `MemoryLayer::L2`.
- `ProjectScopeManager`, code indexer, symbol-memory links, project KG.

Best mechanisms:

- FTS for exact symbols/errors.
- code symbol graph.
- project KG.
- incremental file fingerprinting.
- decision lineage.

### L3: Deep Memory

Purpose:

- long-term knowledge, document insights, compressed sessions, historical observations, low-frequency but reusable knowledge.

Authority:

- evidence-backed active claims can be promoted; stale or superseded claims remain historical.

Runtime role:

- Trace and Pattern.

Implementation:

- existing `MemoryLayer::L3`.
- verbatim evidence and compressed summaries.

Best mechanisms:

- hybrid FTS/vector retrieval.
- temporal state.
- cluster distillation.
- cold archive with path recall.

### L4: Shared Collective

Purpose:

- team memory, cross-agent decisions, delegation results, peer observations, shared project context.

Authority:

- consensus and role reputation matter, but cannot override L0 or verified project facts.

Runtime role:

- Pattern and shared Orientation.

Implementation:

- existing `MemoryLayer::L4`.
- `SharedLayer`, L4 event bus, agent directory, reputation, memory sync.

Best mechanisms:

- scope/visibility fence.
- event-driven peer updates.
- consensus/conflict records.
- parent_session_id and task lineage.

## Runtime Organization Model

### Trace

Raw or near-raw experience:

- session messages.
- tool outputs.
- documents.
- file observations.
- agent transcripts.

Trace is high volume and mostly cold. It is preserved for evidence and reconstruction.

### Pattern

Structured meaning extracted from traces:

- decisions.
- preferences.
- entity facts.
- recurring errors.
- code relationships.
- document topic clusters.

Pattern is the navigational fabric of memory.

### Orientation

Current effective knowledge:

- active L0/L1.
- current project doctrine.
- accepted architecture.
- active task state.
- relevant team decisions.

Orientation is small, authoritative, and directly injected into session/agent context.

## Minimal Core Data Model

Do not introduce many conceptual stores. Normalize around five concepts.

### Atom

The one interpreted memory unit.

Maps to current `MemoryEntry`.

Required fields:

- id.
- layer.
- scope.
- source.
- content/title.
- confidence.
- salience.
- state.
- validity.
- source_agent.
- session_id.
- evidence pointer.

### Evidence

Immutable source material.

Maps to current `VerbatimSink`, blob store, session events, tool sandbox, and imported documents.

### Link

Typed relationship.

Unifies:

- `MemoryEntry.relations`.
- KG triples.
- symbol-memory links.
- session links.
- agent links.
- supersedes/contradicts/supports.

### State

Temporal lifecycle state:

- candidate.
- active.
- conflicted.
- superseded.
- stale.
- archived.

### Recall

Audit record:

- query/intent.
- selected atoms.
- omitted atoms.
- reasons.
- evidence pointers.
- conflicts.
- budget.

## Lifecycle

Every session/agent turn must pass through the same loop:

```text
Bind -> Prepare -> Observe -> Relate -> Judge -> Distill -> Activate/Archive -> Explain
```

### Bind

Bind:

- session_id.
- project_id.
- agent_id.
- team_id.
- task_id.
- model/context budget.

### Prepare

Build a `MemoryContextPacket`:

- orientation.
- supporting patterns.
- warnings.
- conflicts.
- evidence pointers.
- dropped/omitted reasons.

### Observe

Capture session messages, tool outputs, and agent results as trace/evidence.

### Relate

Attach links:

- entity.
- symbol.
- session.
- agent.
- project.
- decision lineage.
- contradiction/supersession.

### Judge

Apply:

- authority.
- confidence.
- recency.
- repetition.
- scope.
- user correction.
- code/test verification.

### Distill

Convert repeated traces into patterns and stable patterns into orientation.

### Activate/Archive

Keep current orientation bounded. Archive does not delete.

### Explain

Every injected memory must be able to answer:

- why this?
- why now?
- from what evidence?
- why not the older version?

### Critical Integration Gaps

1. No MemoryKernel boundary.
   Runtime, sub-agents, JPS, API, and TUI call `CognitiveContextManager` directly.

2. Session/project binding is incomplete.
   Runtime sets `active_agent=primary` but does not uniformly bind session/project/task before every memory lifecycle operation.

3. L0/L1 governance is not yet productized.
   WriteGuard exists, but protected mutation, audit, proposal, and user approval paths are not unified.

4. Relations are fragmented.
   `relations_json`, KG triples, symbol links, and session/agent links are not one path API.

5. State is implicit.
   Confidence/staleness exist, but candidate/active/superseded/conflicted/archived is not a first-class lifecycle.

6. Recall is still mostly retrieval.
   It should become path-based orientation selection with explanation.

7. Large-scale memory needs cold reachability.
   `VerbatimSink`, ToolSandbox, vector, FTS, and KG exist, but there is no single cold-to-active promotion policy.

## Reference Systems Review

This section is based on local inspection of sibling `agents` implementations. The goal is not to copy their product metaphors. The goal is to extract their strongest mechanisms and fit them into Cowd's five-layer governance plus Trace/Pattern/Orientation runtime model.

### MemPalace

Useful mechanisms:

- scope-first organization.
  MemPalace's wing/room/hall/tunnel structure is valuable because it makes retrieval predictable before ranking begins. For Cowd, this maps to `MemoryScope`, `ProjectScopeManager`, agent scope, session scope, and task lineage.

- bounded wake-up.
  Its L0/L1 wake-up model keeps always-loaded context small, then loads L2/L3 only when a topic appears. Cowd should preserve this discipline: L0/L1/L2 orientation must be bounded, and L3/L4 should enter through recall paths.

- closet-like pointer layer.
  The closet layer is useful as a compact topic/entity pointer to evidence, not as a separate user-facing store. Cowd should implement this as Pattern indexes that point to Evidence, never as another memory concept.

- graph traversal from shared rooms.
  MemPalace uses shared room names across wings as tunnels. Cowd should generalize this with typed `MemoryLink` path recall across project, session, agent, entity, symbol, and decision links.

- hybrid candidate union.
  Its searcher treats vector retrieval, BM25, and closet hits as candidate/ranking signals. Cowd should use the same principle: vector is one candidate source, FTS and links are mandatory candidate sources.

- temporal knowledge graph.
  The entity triple design with validity windows matches Cowd's need for "forgotten does not mean deleted". Current facts should be active; superseded facts remain historically queryable.

- fail-soft large corpus handling.
  The graph builder explicitly skips bad metadata rather than failing a whole query. Cowd memory paths must follow this rule: one corrupted atom/evidence/link cannot break a session.

Rejected or constrained:

- Chroma cannot become Cowd's required core dependency.
  Cowd already has SQLite/FTS and optional vector configuration. External vector backends remain optional accelerators.

- the palace metaphor should not leak into Cowd's core API.
  Cowd should expose atoms, evidence, links, state, and recall packets, not drawers/closets/wings as first-class product nouns.

- automatic import of legacy local files is not allowed.
  Consistent with the session decision, local memory/session files can be passively imported by user action, not silently consumed at startup.

### opencode

Useful mechanisms:

- event-sourced session core.
  opencode defines structured session events and projects them into queryable messages, usage, agent/model state, tool calls, and session metadata. Cowd should use the same principle for memory: raw Trace events remain immutable, and current memory views are projected from them.

- projector boundary.
  Its `SessionProjector` is the clean separation between event stream and database state. Cowd needs an equivalent memory projector: Observe writes Trace, projector updates Atom/Link/State/Recall views.

- aggregate-scoped sequencing.
  Events are sequenced per aggregate. Cowd should sequence memory lifecycle events by session_id/project_id/agent_id so concurrent agents cannot corrupt lifecycle state.

- service interfaces over raw storage.
  Session list/get/messages/context operations sit behind a service boundary. Cowd's API/TUI/runtime should call `MemoryKernel`, not `CognitiveContextManager` or store internals directly.

- state editor pattern.
  opencode's state module serializes committed transforms and rebuilds views deterministically. Cowd can use the same concept for active orientation: committed memory state transitions produce current orientation, not ad-hoc mutation.

Rejected or constrained:

- Cowd does not need to clone opencode's full Effect/Drizzle architecture.
  The transferable idea is event -> projector -> service, not the TypeScript stack.

- memory should not become a generic session event dump.
  Session events are Evidence/Trace. Memory begins when interpretation creates Atom/Link/State.

### Hermes

Useful mechanisms:

- task-local session context.
  Hermes replaced process-global environment session state with `contextvars` to avoid concurrent message contamination. Cowd needs an equivalent invariant: active session/agent/project/task must be passed explicitly through `MemoryTurnContext`, never stored as ambient mutable global state.

- structured stream events.
  Hermes separates "what happened" from platform rendering. Cowd should separate memory lifecycle events from TUI/WebUI presentation. UI consumes packets and traces; it does not decide memory meaning.

- memory and heap monitoring.
  Hermes logs memory baselines, high-water marks, and shutdown snapshots. Cowd should add memory subsystem telemetry: prepare latency, recall candidate counts, packet token size, degraded reason, store errors, and background distillation cost.

- runtime footer/status.
  Hermes exposes compact model/context/cwd status. Cowd should expose compact memory status: active layer budget, recall confidence, degraded state, conflict count, and source scope.

- TUI store isolation.
  Hermes TUI uses small stores and gateway event handlers instead of letting UI components own runtime state. Cowd TUI memory views should subscribe to memory packet/state events rather than calling deep memory internals.

- session lifecycle cleanup.
  Hermes resets visible history, writes active-session hints best-effort, and prunes caches without blocking session creation. Cowd should use best-effort memory cleanup and never let cache/telemetry failure block session flow.

Rejected or constrained:

- Hermes' gateway/platform breadth is not the target for Cowd memory.
  Cowd should adopt concurrency and observability practices, not expand memory into a platform adapter layer.

- UI monitoring is not memory governance.
  Status panels explain memory state; they do not decide authority or activation.

## Integrated Design Amendments

### Five Layers As Control Plane

The user's five-layer framework remains the control plane:

- L0 defines non-negotiable identity, doctrine, and protected constraints.
- L1 defines stable habits, preferences, and operating instincts.
- L2 defines project truth, code facts, architecture, and current decisions.
- L3 preserves deep historical/document/session memory.
- L4 shares team/agent knowledge under visibility and authority rules.

Trace/Pattern/Orientation is the runtime data plane:

- Trace records what happened.
- Pattern organizes what it probably means.
- Orientation selects what is currently effective.

The correct synthesis is:

```text
Layer = who may write, see, override, and activate.
Trace/Pattern/Orientation = how information flows.
MemoryKernel = the only runtime boundary that applies both.
```

### Best Mechanisms Per Layer

L0 Constitution:

- storage: deterministic SQLite row plus version history.
- activation: always explicit and bounded.
- mutation: proposal -> audit -> approval -> activate.
- recall: direct by key, never vector-only.
- tests: protected writes rejected unless source is user/system-approved.

L1 Core Instinct:

- storage: atoms with evidence, confidence, reinforcement count, and supersession.
- extraction: user corrections, repeated behavior, explicit preferences.
- activation: small orientation packet with conflict warnings.
- recall: direct scope + FTS + recency/reinforcement scoring.
- tests: user correction supersedes inferred habit; stale habit remains historical.

L2 Project Mind:

- storage: project atoms, symbol links, decision lineage, test/code evidence pointers.
- extraction: file fingerprints, code symbol graph, test failures, architecture decisions.
- activation: current project orientation and active task facts.
- recall: FTS for exact symbols/errors, path recall through symbol/entity/session links, optional embedding for prose docs.
- tests: verified code/test evidence beats stale assistant inference.

L3 Deep Memory:

- storage: immutable evidence plus compressed atoms and cluster patterns.
- extraction: background distillation from sessions, documents, and tool outputs.
- activation: only via path recall and explicit relevance.
- recall: candidate union from FTS, links, vector, and temporal filters.
- tests: large cold corpus remains queryable while context packet stays bounded.

L4 Shared Collective:

- storage: agent/team atoms with visibility, reputation, parent_session_id, task lineage.
- extraction: sub-agent outcomes, joint problem solving results, handoffs, peer consensus.
- activation: shared orientation only when scope permits.
- recall: agent/task/session links plus conflict/consensus records.
- tests: private peer memory never leaks; consensus cannot override L0 or verified L2.

### Memory Lifecycle Events

Introduce explicit lifecycle events, projected into current memory state:

- `memory.trace.recorded`
- `memory.atom.proposed`
- `memory.atom.activated`
- `memory.atom.superseded`
- `memory.atom.archived`
- `memory.link.created`
- `memory.conflict.detected`
- `memory.orientation.prepared`
- `memory.recall.explained`

These events should be aggregate-scoped by at least `session_id`, and when available also by `project_id`, `agent_id`, and `task_id`.

### Passive Import Only

For memory as well as sessions:

- no JSONL as canonical storage.
- no startup auto-import.
- if local legacy files exist, show a passive import notice.
- import writes Evidence first, then runs normal Observe/Relate/Judge projection.
- failed imports create a degraded report, not a runtime crash.

### Observability Requirements

Every prepare/recall/distill operation records:

- latency.
- layer budget.
- candidate counts by source: FTS, link, vector, recent, pinned.
- selected orientation count and token estimate.
- degraded reason if any backend failed.
- conflict/supersession count.
- evidence pointer count.

This is required for enterprise-grade reliability. Without it, large-scale memory failures become invisible.

## Best Implementation Choices

### Exact And Structured Recall

Use:

- SQLite FTS5.
- symbol index.
- scope filters.
- temporal state filters.

Reason:

- exact identifiers, errors, code names, and decisions must not depend on embeddings.

### Semantic Recall

Use:

- external embedding configuration already present in `VectorConfig`.
- vector search only as candidate generation.
- re-rank with FTS, scope, authority, recency, and relation distance.

Reason:

- embeddings are useful but not authoritative.

### Path Recall

Use:

- existing KG/symbol links/relations first.
- add a unified link table/interface.
- bounded BFS or Dijkstra-like scoring by relation type, distance, salience, and authority.

Reason:

- memory recall is path finding, not chunk similarity.

### Distillation

Use:

- deterministic heuristics for first pass.
- optional configured LLM summarizer for cluster naming and summary.
- preserve evidence pointer.

Reason:

- model capability helps interpretation, but source of truth must stay inspectable.

### Conflict And Authority

Use:

- extend existing `FactChecker` and `ConflictResolver`.
- add general claim keys beyond toy triples.
- authority scoring:
  - L0/user explicit.
  - code/test/tool verified.
  - project decision.
  - multi-agent consensus.
  - assistant inference.
  - compressed/imported low-confidence.

Reason:

- current active knowledge must be clean; old knowledge remains recoverable.

### Large Scale

Use:

- hot orientation cache.
- warm FTS/vector/link indexes.
- cold evidence/verbatim/blob.
- background distillation.
- bounded prepare_context budget.

Reason:

- all information can be findable without all information being active.

## Phase Plan

The critical path is:

```text
MemoryKernel -> State/Links -> Orientation Packet -> Governance -> Distillation -> Product Surfaces
```

Parallel work is allowed only when it does not bypass this path.

- UI work can begin after `MemoryContextPacket` has a stable read model.
- telemetry can begin with Phase 1 and expand through all phases.
- import notices can begin after Evidence write paths are stable.
- large-scale benchmarks can be scaffolded early, but pass/fail targets become meaningful after Phase 4.

Goal:

- create a single lifecycle boundary without breaking existing behavior.
- remove ambient mutable session/agent assumptions from memory entry points.

Work:

- add `MemoryKernel` wrapper in memory crate or runtime adapter module.
- add `MemoryTurnContext`.
- adapt runtime pre-turn prepare through kernel.
- adapt post-turn maintenance through kernel.
- keep `CognitiveContextManager` as backend.
- bind session_id, project_id, agent_id, team_id, task_id per operation.
- return structured degraded results when memory backend fails.
- add basic telemetry for prepare/post_turn latency and degraded reason.

## Implementation Rules

1. Do not replace existing memory modules at once.
   Wrap, normalize, and migrate gradually.

2. Do not make embedding mandatory.
   External embedding config remains optional; FTS/link/path recall must work alone.

3. Do not treat graph/vector/wiki as independent product concepts.
   They are indexes/views over atoms.

4. Do not delete forgotten memory by default.
   Archive or supersede.

5. Do not allow memory errors to crash session/agent execution.
   Report degraded memory state.

6. Do not let sub-agents bypass governance.
   All agent memory writes go through MemoryKernel.

Minimal first API:

```rust
pub struct MemoryTurnContext {
    pub session_id: String,
    pub project_id: Option<String>,
    pub agent_id: String,
    pub team_id: Option<String>,
    pub task_id: Option<String>,
}

pub struct MemoryKernel {
    manager: Arc<CognitiveContextManager>,
}

impl MemoryKernel {
    pub async fn prepare(&self, ctx: &MemoryTurnContext, query: &str, messages: &[Message])
        -> MemoryKernelResult<PreparedContext>;

    pub async fn post_turn(&self, ctx: &MemoryTurnContext, messages: &mut Vec<Message>)
        -> MemoryKernelResult<()>;
}
```

First acceptance:

- no direct new runtime call to `CognitiveContextManager::prepare_context` outside kernel.
- session/agent context is bound before prepare/post-turn.
- degraded memory path is structured and non-fatal.

## Final Shape

The final memory system should feel simple:

```text
L0-L4 decide who may know, write, and override.
Trace/Pattern/Orientation decide how knowledge lives.
MemoryKernel decides how every session and agent uses it.
Links decide how cold knowledge becomes reachable.
State decides what is active, historical, superseded, or archived.
Recall decides the shortest reliable path to current valid orientation.
```

That is the pure architecture.

It uses the strengths already present in Cowd, but removes accidental complexity by giving every part one role.
