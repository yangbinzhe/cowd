# Cowd v0.8.10 AI Capability Framework Master Plan

## 版本目标

v0.8.10 的目标不是继续堆叠零散功能，而是把 Cowd 收敛成一套高完成度、可验收、可持续演进的企业级 AI 能力框架。

核心设计目标：

- Kernel-first：Session、Memory、Task、Event、Audit 必须形成稳定服务边界，TUI/WebUI/API 不再各自拼状态。
- Continuous AI：`--solo` 和 `--yolo` 具备连续执行、恢复、取消、审计和可解释上下文能力。
- Product-grade interaction：TUI 对齐 Codex/OpenCode/Hermes 的核心交互体验，WebUI 只保留一套最完整实现。
- Observable reliability：所有关键失败路径必须可降级、可观测、可测试、可清理。
- Release discipline：每个阶段先写契约测试或场景测试，再实现，再运行专项 gate 和全量 gate。

## 缺口清单

### A. SessionKernel 未完全内核化

现实状态：

- Kernel 已存在，但 `AppState` 仍保留兼容字段。
- API 主路径中仍有直接读取 `sessions/unified_store/event_bus` 的历史访问点。
- daemon unix handler、TUI、CLI resume、session lifecycle manager 尚未完全统一到 Kernel。
- create/list/detail/messages/events/delete/compact/update 仍由 route handler 编排，缺少 Kernel command API。

需要完成：

- `SessionKernel` 提供 create/list/get/delete/messages/events/update/compact/subscribe 的服务方法。
- `UnifiedSessionStore` 成为冷事实源，`ActiveSessions` 只负责热 runtime。
- 所有事件写入必须有统一 sequence、payload、审计来源。
- 兼容字段只允许测试和迁移期构造使用，业务入口不得继续直接读取。

### B. Memory/CognitiveKernel 实战化不足

现实状态：

- Memory store、L4、prepare_context、symbol links 等能力存在，部分 gate 已覆盖。
- TUI/WebUI 能展示 memory 面板，但对 enabled/disabled/degraded、召回来源、最近写入、token 节省、长任务上下文贡献展示不完整。
- memory 初始化失败、DB 锁、索引异常、后台摄入失败等路径缺少产品级降级测试。

需要完成：

- 建立 `CognitiveKernel` 或等价门面，统一 prepare、recall、write、status、degraded report。
- 长任务上下文必须包括目标、阶段、关键决策、失败恢复、未完成项。
- TUI/WebUI 显示 memory 状态和召回解释，不渲染原始内部结构。
- Memory 失败不阻塞 TUI 首屏、API health 和非 memory 会话。

### C. 连续任务/YOLO 缺少持久任务内核

现实状态：

- `--yolo` 已接入模式和提示，但还不是完整 durable task engine。
- 没有统一的 Goal/Task 状态机、阶段审查、恢复点、取消语义、进度事件和审计记录。

需要完成：

- 新增 Task/Goal Kernel：pending/running/reviewing/completed/blocked/cancelled/failed。
- 每个阶段必须有 objective、plan、acceptance、test commands、artifacts、review result。
- `--solo` 保持权限策略，`--yolo` 在此基础上启用连续执行直到完成定义满足或进入明确 blocked。
- TUI/WebUI 都能看到当前任务状态、阶段、日志、测试结果和恢复入口。

### D. TUI 交互仍需专项打磨

现实状态：

- TUI 组件多，已有 SessionSidebar、MemoryPanel、Gateway、L4、Performance 等测试。
- tmux smoke 目前主要证明首屏可启动和 YOLO 可见。
- 长任务进度、工具事件、审批、memory、session、性能还没有形成一个稳定 cockpit。

需要完成：

- 首屏必须稳定呈现：model、mode、session、permission、memory、tools、task、health。
- 输入区、命令区、事件 timeline、工具详情、审批、任务进度形成统一交互模型。
- 长输出和流式事件不能阻塞输入。
- 快捷键和 slash commands 与 Codex/OpenCode/Hermes 的高价值模式对齐，但实现必须服务 Cowd 现有能力。

### E. WebUI 仍需企业级场景矩阵

现实状态：

- 已只保留一套根级 WebUI。
- WebUI unit 覆盖 39 个测试，Playwright 目前只有最小 E2E。
- Chat/session/SSE/history/delete/memory/audit/profile/workspace/approval 面板仍缺少真实场景矩阵。

需要完成：

- 建立 WebUI E2E matrix：无鉴权、有鉴权、建会话、发消息、SSE、刷新恢复、删除、memory、audit、approval、workspace。
- 后端 mock provider 场景化运行，浏览器断线/重连/offline cache 有测试。
- WebUI 工作台信息架构收敛：会话主线、上下文能力、审计和控制中心一体化。
- Service worker 缓存策略持续验证，避免旧脚本污染。

### F. Release Gate 2.0 和观测能力不足

现实状态：

- 当前 gate 已可守住主路径。
- 缺少测试产物归档、日志断言、DB 状态断言、场景矩阵脚本和失败模式测试。
- 第三方 `imap-proto v0.10.2` 仍有 future-incompat warning，需要依赖路线决策。

需要完成：

- 新增 scenario scripts：TUI long task、WebUI chat matrix、memory degraded、session DB audit。
- gate 自动检查日志关键字、SQLite 记录、端口、tmux、浏览器进程。
- 所有服务型测试结束必须清理 tmux/session/port/temp db。
- 对第三方 warning 给出升级、替换、隔离或暂缓说明。

## 并行执行路线

可并行 lane：

- Lane A：SessionKernel 服务化。产物是 Kernel command API、API/daemon/TUI 迁移、session contract tests。
- Lane B：CognitiveKernel 实战化。产物是 memory status/degraded/recall explain API 和 UI 消费。
- Lane C：Task/Goal/YOLO 内核。产物是 durable task state、阶段审查、恢复/取消、事件持久化。
- Lane D：TUI cockpit。产物是统一首屏、timeline、task panel、approval/tool/memory/status 聚合。
- Lane E：WebUI workbench。产物是唯一 WebUI 的主工作台和 E2E matrix。
- Lane F：Release/observability。产物是 release gate 2.0、日志/DB/port/tmux/browser 清理检查。

并行边界：

- Lane A 先定义 session/event DTO，Lane C/D/E 只能消费稳定 DTO。
- Lane B 先定义 memory status/recall explain DTO，D/E 只能消费 DTO。
- Lane F 可先补脚本骨架，但必须在 A/B/C 的接口稳定后补完整断言。
- 禁止 TUI/WebUI 绕过 Kernel 直接读取内部 store 或 runtime。
