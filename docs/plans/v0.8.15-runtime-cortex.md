# Cowd v0.8.15 Runtime Cortex Plan

## Version Position

v0.8.15 turns the current v0.8.14 runtime foundation into a focused AI core.

The goal is not to add a heavy platform layer. The goal is to make the existing
session, context, memory, task, agent, TUI, WebUI, and runtime trace capabilities
operate as one coherent AI runtime:

```text
Intent -> SessionLifecycle -> RuntimeRun -> ContextEnvelope
       -> Agent/Tool Action -> Evidence -> MemoryPulse
       -> Review/Reconcile -> Next Action
```

This branch is the product integration branch. Two spike branches validate the
largest design uncertainties:

- `spike/v0.8.15-high-capability-core`: agent collaboration and living memory.
- `spike/v0.8.15-lean-runtime-core`: minimal runtime trace, context stability,
  and performance pressure.

The final product should absorb only the mechanisms that prove useful under a
shared evaluation baseline.

## First Principles

1. AI value comes from a strong loop, not from module count.
2. Session is the lifecycle container.
3. Context is the active model input contract.
4. Memory is long-term orientation, not a prompt stuffing store.
5. Agent collaboration must reduce uncertainty, risk, or latency enough to pay
   for coordination cost.
6. Runtime trace is the explanation spine for every action.
7. UI consumes stable DTOs; it must not infer internal state from private stores.
8. Slow or broken subsystems degrade locally and never collapse the main turn.

## Target Kernels

### Session Kernel

Owns create, activate, run, pause, resume, fork, archive, delete, and snapshot.
SQLite remains the canonical runtime store. JSONL is only an explicit import or
export artifact.

### Runtime Trace Kernel

Owns a tree of runtime work:

```text
RuntimeRun
  - run_id
  - parent_run_id
  - kind: main_turn | yolo_goal | agent_task | tool_call | context_build | memory_op | review
  - profile
  - status
  - summary
  - refs
  - started_at / completed_at / duration_ms
  - error
```

RuntimeRun is the minimum durable explanation object. It should be small enough
to write on hot paths and rich enough to reconstruct what happened.

### Context Runtime Kernel

Owns model input. Every execution mode uses one `ContextEnvelope` shape with
different profile leases:

- Stable Head
- Runtime Header
- Active Task
- Working Set
- Memory Recall
- Agent Notes
- Omitted Index
- User Turn

Stable Head must remain hash-stable across dynamic tail changes to improve
provider prompt cache behavior and reduce semantic drift.

### Memory Kernel

Owns the living memory loop:

```text
Sense -> Encode -> Associate -> Judge -> Consolidate -> Orient -> Act -> Reflect
```

The implementation remains pure. Advanced behavior must be expressed through the
existing primitives: evidence, atoms/entries, links, state, recall, and
maintenance candidates. Memory never blocks a user turn on background enrichment.

### Agent Orchestration Kernel

Owns agent work as structured tasks, not ad hoc sub-prompts:

```text
AgentTask
  - task_id
  - parent_run_id
  - role
  - objective
  - context_ref
  - status
  - result_summary
  - evidence_refs
  - confidence
  - conflicts
```

Agent collaboration should be enabled only when expected value is positive:

```text
spawn_value = parallelism_gain
            + uncertainty_reduction
            + risk_reduction
            - context_cost
            - coordination_cost
```

### Interaction Kernel

TUI and WebUI should show the same runtime facts:

- current run tree
- active context and omissions
- agent tasks and conflicts
- evidence drilldown
- memory maintenance
- yolo goal phase and recovery status
- degraded sources

## Multi-Agent Collaboration Modes

### Producer / Reviewer

One agent produces an artifact. A second agent reviews evidence, tests, and risk.
This mode is high value for code changes, migration work, and release gates.

### Parallel Explore / Reducer

Several agents explore independent uncertainty areas. The parent runtime reduces
results into a single decision with evidence refs and confidence.

### Debate / Arbiter

Agents intentionally inspect a hard decision from different perspectives. The
arbiter records agreement, disagreement, and the authoritative decision.

### Memory Curator

A focused agent reviews memory candidates, conflicts, stale entries, and
authority promotion. It proposes maintenance actions without silently mutating
protected memory.

## Phase Plan

### Phase 0: Branch And Evaluation Baseline

Acceptance:

- release and two spike worktrees exist.
- this plan exists on the release branch.
- `scripts/v0815_eval.sh` runs the shared local baseline.
- no test service, port, or tmux residue remains.

### Phase 1: Runtime Trace Tree

Acceptance:

- root turns, context builds, agent tasks, tool calls, and memory ops can be
  linked through parent ids or refs.
- recent run queries remain paged and fast.
- a child failure records degraded state without failing the whole turn.

### Phase 2: Context Cortex

Acceptance:

- every envelope explains selected and omitted content.
- Stable Head hash survives dynamic tail changes.
- yolo, solo, review, resume, sub-agent, and collaboration profiles use
  different leases without copying logic.
- context pressure degrades by source class rather than by global truncation.

### Phase 3: Memory Pulse

Acceptance:

- memory maintenance candidates are durable.
- stale means out of foreground, not deleted.
- conflict candidates keep both sides and their evidence.
- orientation packets remain small and authoritative.

### Phase 4: Agent Orchestration

Acceptance:

- agent work is represented by structured AgentTask records.
- parent runtime can merge results, evidence, conflicts, and confidence.
- sub-agent failure is local and observable.
- collaboration is only spawned when it has a positive expected value.

### Phase 5: Continuous Yolo Goal

Acceptance:

- yolo goals have durable phases, artifacts, tests, reviews, and recovery points.
- a single tool or agent failure records a failure node and chooses a recovery
  path where possible.
- completed goals include acceptance evidence.

### Phase 6: Runtime Cockpit

Acceptance:

- WebUI can trace a run to context, agent, evidence, memory, and task state.
- TUI can inspect current run, context pressure, evidence refs, memory
  candidates, and yolo status by keyboard.
- empty, unavailable, and degraded states are explicit.

### Phase 7: Performance And Failure Engineering

Acceptance:

- large session events, large memory stores, and large workspaces are tested.
- hot-path runtime writes remain bounded.
- heavy memory and agent work is deferred, paged, or capped.
- browser, tmux, service, DB, and port scenario tests clean up after themselves.

## Evaluation Scorecard

Each branch is scored on the same dimensions:

| Dimension | Question |
| --- | --- |
| AI effect | Does the mechanism improve task completion, recall, review, or recovery? |
| Simplicity | Is the mechanism understandable and maintainable? |
| Performance | Does it keep hot paths bounded under large state? |
| Failure isolation | Does a local failure remain local? |
| Observability | Can users and developers explain the result without logs? |
| Integration cost | Can it merge into the product branch without re-fragmenting design? |

Decision rule:

```text
strong effect + bounded complexity -> merge into release
strong effect + high complexity -> simplify before merge
weak effect + good performance -> reuse implementation detail only
weak effect + high complexity -> reject
```
