# v0.9.90 IACC Cross-plane Action Bridge

## Goal

Connect governed IACC recommended actions to the existing cross-plane control
plane without turning IACC into a source-system executor.

IACC remains the operating-decision layer. Cross-plane remains responsible for
identity, grant matching, policy, audit, idempotent execution receipts, and
future live dispatch adapters.

## Runtime Contract

`IaccActionExecution` now keeps cross-plane bridge receipts:

- `cross_plane_receipts`

New contract:

- `IaccCrossPlaneBridgeReceipt`

The receipt stores:

- IACC execution id;
- cross-plane execution receipt id;
- cross-plane status;
- cross-plane dispatch status;
- audit record id;
- bridge timestamp.

Duplicate cross-plane receipt ids are deduplicated on the IACC execution so
idempotent replays do not inflate the IACC action history.

## API

New route:

```text
POST /api/iacc/executions/:id/cross-plane/execute
```

Request fields:

- `mode`: `dry_run` or `commit`;
- `idempotency_key`;
- `actor_principal`;
- `actor_identity_ref`;
- `source_channel`;
- `requested_capability`;
- `provider_account`;
- `target_ref`;
- `resource_ref`.

The bridge derives a `CrossPlaneAction` from the IACC execution and request.
Default capability is `channel.feishu.send_text`, because this version proves
the notification/task-dispatch bridge first. Real ERP/MES/SRM command adapters
can be introduced later using the same cross-plane policy and receipt surface.

`GET /api/iacc/health` now includes:

- capability: `cross_plane_action_bridge`

## Execution Semantics

The bridge does not perform live platform dispatch. It records a cross-plane
execution receipt and audit record:

- `dry_run + allow` -> cross-plane status `planned`, dispatch status `dry_run`;
- `commit + allow` -> status `planned`, dispatch status
  `human_review_required`;
- non-allow policy decision -> status `blocked`, dispatch status
  `policy_blocked`.

This preserves the enterprise boundary: IACC can issue a governed task into the
execution plane, but high-risk work still needs identity/grant/policy checks and
human review before live system mutation.

## Acceptance

Runtime tests prove:

1. an IACC execution can attach a cross-plane receipt;
2. repeated receipt ids are deduplicated;
3. feedback closure still works after a bridge receipt is attached.

Scenario script:

```text
scripts/v0990_iacc_cross_plane_action_bridge_scenario.sh
```

The gateway scenario proves through API:

1. IACC health exposes schema 9 and `cross_plane_action_bridge`;
2. a verified cross-plane identity and grant can be created;
3. IACC fact -> metric -> evidence -> incident -> analysis -> action execution
   still works;
4. the IACC execution can be bridged to cross-plane;
5. cross-plane execution history contains the generated receipt;
6. idempotent replay returns the same cross-plane receipt and does not duplicate
   the IACC bridge receipt.
