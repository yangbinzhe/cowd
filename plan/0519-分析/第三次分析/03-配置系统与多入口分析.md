# Cowd 第三次深度分析 — 配置系统与多入口分析

> 基于 GitNexus：config crate + runtime/config.rs 双重配置体系，CLI/TUI/Server 三入口

## 1. 配置系统架构

### 1.1 双重配置体系（GitNexus 发现的关键问题）

```
┌──────────────────────────────┐  ┌──────────────────────────────┐
│ crates/config/src/lib.rs     │  │ crates/runtime/src/config.rs │
│                              │  │                              │
│ UnifiedConfig                │  │ ConfigLoader                 │
│  ├─ resolve_provider()       │  │  ├─ load() (69行)            │
│  ├─ BudgetConfig             │  │  ├─ parse_mcp_server_config()│
│  ├─ ModelProfile::for_model  │  │  ├─ McpServerConfig          │
│  └─ deserializes_yaml        │  │  └─ parse_optional_approval  │
└──────────────────────────────┘  └──────────────────────────────┘
        独立 config crate                 runtime 内嵌配置
```

**GitNexus 数据**：
- `config/src/lib.rs` 有 `resolve_provider` + `BudgetConfig` + `ModelProfile`
- `runtime/src/config.rs` 有 `ConfigLoader.load` + `parse_mcp_server_config`
- 两套系统**无直接依赖**关系，通过 `config-default.yaml` 桥接

### 1.2 配置优先级（5 级）

```
CLI 参数 (--model, --yolo, --port)        ← 最高
  ↓
环境变量 (COWD_*, CC_*)                    ← 系统级
  ↓
Local 配置 (.cowd/config.local.yaml)       ← git-ignored
  ↓
Project 配置 (.cowd/config.yaml)           ← 项目级
  ↓
User 配置 (~/.cowd/config.yaml)            ← 默认
```

### 1.3 三入口架构

| 入口 | 核心函数 | 文件 | 行数范围 | 运行时模型 |
|------|---------|------|---------|-----------|
| CLI REPL | `run_repl` → `run_tui_repl` | main.rs | 2,634-2,783 | 同步阻塞 |
| TUI | `run_tui_repl` | main.rs | 2,634-2,783 | 单线程事件循环 |
| HTTP Server | `start_http_server` | server.rs | 533-825 | tokio 异步 |

## 3. 缺陷与弊端

### 🔴 P0: main.rs 巨型单体
**问题**：`crates/cowd-cli/src/main.rs` 承载了 CLI+TUI+Server 所有入口逻辑。
**GitNexus 数据**：
  - run_tui_repl 调用 19 个不同模块（从 context 分析）
  - main.rs 包含 LiveCli 40+ 个方法
  - 同一文件定义 CLI 解析、TUI 渲染、消息格式化、会话管理
**影响**：
  - 编译时间：单文件变更触发全量重编译
  - 测试困难：CLI 逻辑无法独立测试
  - 代码审查：PR 冲突频繁

### 🔴 P0: stdout 与 TUI 渲染冲突（已有分析确认）
**GitNexus 验证**：
  - `consume_stream` (171行，line 6663-6834) 直接写 stdout
  - `format_tool_call_start` / `format_tool_result` 直接 println!
  - `draw` (render.rs) 使用 ratatui Frame
  - **8 个 stdout 泄漏点**已在上次分析中编号

### 🟡 P1: 配置系统分裂
**问题**：config crate 和 runtime/config.rs 两套系统并存。
**影响**：
  - 新增配置项需两处修改
  - 运行时配置加载必须交叉验证
  - 开发者困惑：应该在哪里添加配置？
**建议**：统一到 config crate，runtime 通过 trait 消费。

### 🟡 P1: Server 和 TUI 共享 Runtime 但有不同生命周期
**问题**：ConversationRuntime 设计为同步阻塞模型，但 Server 需要异步。
**GitNexus 数据**：
  - `run_turn_async()` 在 conversation.rs 中包装了同步调用
  - `stream_with_provider()` 在 executor.rs 使用了 tokio
  - Server 通过 `send_message_stream_handler` 桥接到 SSE
**影响**：Server 路径中包含 `.block_on()` 调用，在高并发下可能阻塞 tokio 线程池。

### 🟢 P2: WebUI 与后端 API 版本不同步
**问题**：WebUI (JS) 的 API 调用与 Server (Rust) 的路由定义无编译时检查。
**GitNexus 数据**：api.js (582行) 手动定义所有 endpoint，无法验证类型安全。

### 🟢 P2: 配置热重载缺失
**问题**：配置文件变更后需要重启才能生效。
**GitNexus 数据**：无 hot-reload 相关符号。

## 4. 配置系统最大化价值方案

1. **main.rs 拆分**：
   - `crates/cowd-cli/src/cli.rs` — CLI 入口
   - `crates/cowd-cli/src/tui/mod.rs` — TUI 入口（已部分实现）
   - `crates/cowd-cli/src/server/mod.rs` — Server 入口（server.rs 已有）
2. **配置统一**：合并 config crate 和 runtime/config.rs 到统一的 `config` crate
3. **异步 Runtime 统一**：将 ConversationRuntime 改为 async-first，CLI 通过 `block_on` 消费
4. **WebUI 类型安全**：生成 TypeScript 类型定义（通过 schemars/json-schema）
5. **配置 watch**：使用 `notify` crate 监听配置变更并重新加载
